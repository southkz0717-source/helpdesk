# Helpdesk тестілеу стратегиясы

11-ЗЖ, 1-тапсырма. Құжатта тестілеу деңгейлері, автоматтандыру көлемі, тест деректері, орталар және ФЕТ тексерулері сипатталады.

**Негізгі қағида** (11-дәріс): сапаны тестілеушілер жасамайды, олар бар нәрсені өлшейді. Сапа ертерек қабылданған шешімдермен жасалады: қабылдау критерийлері, ревью, автотесттер, quality gates. Сондықтан тексерулердің көбі соңында емес, **әр PR-да автоматты түрде** жүреді.

## 2. Автоматтандыру көлемі

**Не автоматтандырылған:** бұзылса ең қымбатқа түсетін және ең жиі тексерілетін нәрсенің бәрі.

- SLA есебі: P1–P4 мерзімдері. Қате болса, бизнес міндеттемелері бұзылады.
- Мәртебе өтулері: рұқсат етілмеген өтуге тыйым.
- Деректерді сақтау: WAL, том, иесіздендіру. Бұл #7 инцидентінен және жүктеме тестінен кейін қосылды.
- Барлық API эндпоинттері және валидация.
- Үш тілдегі интерфейс.
- Пайдаланушының негізгі сценарийлері браузерде.

**Не қолмен қалады және неге:**

| Не | Неге автоматтандырылмаған |
|---|---|
| UAT | Мақсаты — тапсырыс беруші жүйенің оның міндетін шешетінін өзі тексеруі. Мұны автоматтандыруға болмайды |
| Зерттеу тестілеуі | Сценарийде жоқ ақауларды табу үшін |
| Скринридермен тексеру (NVDA) | Нәтижені адам бағалайды |
| Көшірмеден қалпына келтіру | Айына бір рет оқу-жаттығу ретінде, runbook бойынша |

**Регресс:** әр PR-да толық жиынтық жүреді. Ол үшін branch protection 5 тексерудің жасыл болуын талап етеді: Lint, Tests, E2E, Security, Build.

**Тұрақсыз тесттер саясаты:** «кейде құлайтын» тест «жақсы уақытқа дейін» өшірілмейді, ол бірден жөнделеді немесе жойылады. Оған сену жоғалса, тест болмағаннан да нашар. E2E тесттер құласа, CI Playwright trace-ін (`e2e-traces` артефакт) сақтайды. Ол әр қадамның скриншоты мен желілік сұраныстарын көрсетеді.

**PM-ге арналған метрика** қарапайым: толық жүгірту қанша уақыт алады (қазір ~2 минут) және `main`-дегі іске қосулардың қаншасы жасыл (**Actions → CI**, `branch:main` сүзгісі).

## 3. Тест деректері

| Деңгей | Деректер қайдан | Иесіздендіру |
|---|---|---|
| Модульдік / API | Әр тестке бөлек бос SQLite (`tmp_path`) | Қажет емес: синтетикалық |
| E2E | Сессияға бір бос база, әр тест бірегей маркер қолданады (`uuid`) | Қажет емес |
| Жүктеме | Locust синтетикалық өтінімдер жасайды (`load-user-N`) | Қажет емес |
| Демо-стенд / UAT | Продакшен базасының **иесіздендірілген көшірмесі** | `scripts/anonymize.py` |

**Ереже: продакшен базасының көшірмесі иесіздендірусіз стендке түспейді.** 11-дәрістің ескертуі бойынша, бұл дербес деректердің ағып кетуінің ең жиі себебі.

### Иесіздендіру қалай жұмыс істейді

```bash
ANONYMIZE_KEY=<құпия кілт> python scripts/anonymize.py prod.db stand.db
```

| Баған | Не болады | Мысал |
|---|---|---|
| `requester` | Тұрақты бүркеншік атқа **ауыстырылады** (HMAC-SHA256). Бір адам әрқашан бір бүркеншік ат алады, сондықтан «бір адамға қанша өтінім» статистикасы сақталады | `Айгерім Нұрланқызы` → `Пайдаланушы-0427` |
| `title`, `description` | E-mail, телефон, ЖСН (12 сан), карта нөмірі маскаланады | `aigerim.n@mail.kz, +7 701 123 45 67` → `[email], [phone]` |
| `priority`, `status`, күндер | **Сақталады**: дербес деректер жоқ, ал SLA мен жүктеме тестіне керек | — |

Деректер «фамилияны алып тастау» жолымен емес, **ауыстыру** арқылы иесізденеді. Көшірмеден кейін `VACUUM` жасалады, сондықтан ескі мәндер файлдың бос беттерінде қалмайды. Тест (`test_anonymize_copy`) стенд файлының байттарында аттың, e-mail-дің және телефонның жоқтығын тексереді.

Кілт (`ANONYMIZE_KEY`) репозиторийде сақталмайды. Ол болмаса, кездейсоқ кілт алынады.

**Шынайылық:** он жазбада өнімділік мәселесі көрінбейді. Сондықтан жүктеме тесті 2 минутта ~1800 өтінім жасайды, ал UAT алдында стендке кемінде 200 өтінім жүктеу керек (иесіздендірілген көшірме немесе Locust-тың қысқа жүгіртуі).

## 4. Орталар

| Орта | Не | Деректер | Кім пайдаланады |
|---|---|---|---|
| **Локалды** | `uvicorn --reload`, Windows/macOS/Linux | Бос база | Әзірлеуші |
| **CI** | GitHub Actions, `ubuntu-latest` | Әр тестте бос база | Автоматты түрде, әр PR |
| **Демо-стенд** | `docker compose --profile monitoring up -d`: Helpdesk (атаулы томмен) + Uptime Kuma | Иесіздендірілген көшірме | UAT, тапсырыс беруші |
| **Продакшен** | Оқу жобасында жоқ. «Жаю» = GHCR-дегі GitHub Release | — | — |

### Демо-стендті мониторингпен көтеру

```bash
docker compose --profile monitoring up -d
```

1. http://localhost:3001 ашыңыз → әкімші аккаунтын жасаңыз (тек өз компьютеріңізде).
2. **Add New Monitor**:
   - Monitor Type: **HTTP(s) - Keyword**
   - URL: `http://helpdesk:8000/health`
   - Keyword: `"persistent_storage":true`
   - Heartbeat Interval: 60, Retries: 3
3. Монитор екі жағдайда ескертеді: сервис жауап бермесе **және** ол томсыз іске қосылса (#7 инцидент).

Бұл релиз жоспарындағы 1-кері қайтару критерийін іске асырады: `/health` қатарынан 3 рет жауап бермесе.

## 6. Жүктеме тесті

### Тапсырманың қойылымы

«Өнімділікті тексеру» — тапсырма емес. Профиль, нысаналы көрсеткіш және ұзақтық керек.

| Параметр | Мәні |
|---|---|
| **Профиль** | Тізім беті 40%, іздеу 20%, өтінімді ашу 15%, жаңа өтінім 15%, мәртебені өзгерту 10% |
| **Пайдаланушылар** | 200 бір мезгілде, секундына 20-дан қосылады, әрекеттер арасында 1–3 с |
| **Ұзақтық** | 2 минут (шыңдық жүктеме) |
| **Нысана** | p95 < 800 мс, қателер < 1% |
| **Нәтиже** | Тек «өтті / өтпеді» емес: графиктер және нашарлау басталатын нүкте (`loadtest/results/*.html`) |

```bash
pip install -r requirements-load.txt
uvicorn app.main:app --port 8000
locust -f loadtest/locustfile.py --host http://localhost:8000 --headless -u 200 -r 20 -t 2m --html loadtest/report.html
```

Нысана орындалмаса, скрипт `exit code 1` қайтарады.

### Нәтижелер: тест екі ақау тапты

| Көрсеткіш | v0.3.1 (дейін) | v0.4.0 (кейін) |
|---|---|---|
| p95 | **4000 мс** ❌ | **81 мс** ✅ |
| Медиана | 190 мс | 24 мс |
| Қателер | 0,73% (53 × HTTP 500) | 0,01% (1 байланыс үзілісі) |
| `database is locked` | 68 | 0 |
| Өткізу қабілеті | 61 сұраныс/с | 91 сұраныс/с |
| Есептер | [before-v0.3.1.html](../loadtest/results/before-v0.3.1.html) | [after-v0.4.0.html](../loadtest/results/after-v0.4.0.html) |

**1-ақау: `database is locked` → HTTP 500.** SQLite әдепкі режимде бір уақытта тек бір транзакцияға рұқсат береді. 200 пайдаланушымен жазбалар бір-бірін 5 секундтан артық күтіп, қатемен аяқталды.
Түзету: **WAL режимі** (оқушылар жазушыны бұғаттамайды), `busy_timeout = 10 с`, `synchronous = NORMAL`.

**2-ақау: баяу беттер.** Басты бет пен API **барлық** өтінімдерді қайтарды. 2 минуттан кейін олар 1331 болды, сондықтан жауап уақыты база өскен сайын өсті.
Түзету: **беттеу** (бетте 50, API-да әдепкі 100, ең көбі 500) және `(priority, created_at)` индексі.

**Шектеулер:** тест Windows ноутбугында жүрді, ол продакшеннен өзгеше. Нәтиже абсолютті емес, **салыстырмалы**: түзетуге дейін және кейін. Жазбалардың 98-перцентилінен бастап ~2 с «құйрық» қалды. Ол нысанаға (p95) әсер етпейді, бірақ келесі итерацияда зерттеледі.

## 7. Quality gates

| Қақпа | Шарт | Қалай тексеріледі |
|---|---|---|
| Әзірлеуге кіру | Тарихшада қабылдау критерийлері бар | PR шаблоны, ревью |
| PR мержі | 5 тексеру жасыл: Lint, Tests, E2E, Security, Build | Branch protection (ruleset) |
| Релиз алдында | ФЕТ тексерілді, кері қайтару жоспары дайын | Release issue чек-парағы ([release-plan.md](release-plan.md)) |
| Қабылдау алдында | UAT сценарийлері келісілді, стендте иесіздендірілген деректер | [uat.md](uat.md) (2-бөлік) |

Қақпа шынымен қолданылғанда ғана жұмыс істейді: бір рет өткізіп жіберу бәрін құнсыздандырады.

## 8. Тәуекелдер
