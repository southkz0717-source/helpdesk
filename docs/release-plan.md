# Helpdesk релиз жоспары

ЗС 10, 5-тапсырма. Бұл құжат релиздің қашан, кіммен және қалай шығатынын, сондай-ақ қалай кері қайтарылатынын анықтайды.

## 1. Негізгі қағидалар

- **Релиз = `vX.Y.Z` тегі.** Тегті `main`-ге қойғанда [`release.yml`](../.github/workflows/release.yml) тестерді жүгіртеді, `ghcr.io/southkz0717-source/helpdesk:X.Y.Z` бейнесін жариялайды және GitHub Release жасайды. DORA метрикалары үшін «жаю» дегеніміз осы.
- **Нұсқалау — SemVer:** `X` үйлесімсіз өзгерістер, `Y` жаңа функциялар, `Z` түзетулер.
- **Жиі әрі ұсақ.** Бір релизде бір-екі PR болғаны жақсы: тексеру оңай, кері қайтару жеңіл, не бұзылғаны бірден түсінікті (10-дәріс).
- **`main`-ге тек PR арқылы** және 4 тексеру жасыл болғанда ғана ([branch-protection.md](branch-protection.md)).
- **Кері қайтару — қалыпты операция,** жеңілісті мойындау емес. Критерийлері алдын ала цифрмен бекітілген (5-бөлім).

## 2. Рөлдер және жауаптылар

| Рөл | Кім | Не істейді |
|---|---|---|
| Релиз иесі (PM) | _аты-жөні_ | Күнді бекітеді, чек-парақтың орындалуын тексереді, «шығарамыз / кері қайтарамыз» деп шешеді |
| Әзірлеуші | _аты-жөні_ | Тегті қояды, `release.yml` жүгіртуін бақылайды, кері қайтаруды орындайды |
| Тестілеуші | _аты-жөні_ | Релизге дейін стендте тексереді, шығарудан кейін smoke-тест жасайды |
| Кезекші | _аты-жөні_ | Шығарудан кейінгі 24 сағат ішінде алерттерге жауап береді |
| Тапсырыс берушімен байланыс | _аты-жөні_ | Релиз туралы және инцидент кезінде хабарлайды |

Команда шағын болса, бір адам бірнеше рөлді атқара алады. Бірақ **релиз иесі мен кезекшінің аты кестеде міндетті түрде болуы керек:** «бәрі жауапты» дегеніміз «ешкім жауап бермейді» деген сөз.

## 3. Релиз терезелері

Уақыт: Алматы, UTC+5.

| Релиз түрі | Қашан шығады | Кім бекітеді |
|---|---|---|
| Жоспарлы (`Y` немесе `Z`) | **Сейсенбі және бейсенбі, 10:00–16:00** | Релиз иесі |
| Шұғыл түзету, P1/P2 (`Z`) | Кез келген уақытта, тыйым салынған кезеңдерде де | Релиз иесі + кезекші |
| Үлкен өзгеріс (`X`, деректер көшіруі) | Тек сейсенбі, 10:00–12:00, күні бұрын хабарлап | Релиз иесі + тапсырыс беруші |

Неге осы уақыт: шығарудан кейін ақауды түзетуге жұмыс күнінің кемінде 4 сағаты қалуы керек, келесі күн де жұмыс күні болуы керек.

**Тыйым салынған кезеңдер (change freeze)** — тек шұғыл түзетулер шығады:

- жұма 15:00-ден кейін, сенбі, жексенбі («сенбі таңертең жөндейтін ешкім болмаса, жұма кеші шығармаңыз»);
- ҚР мерекелері және олардың алдындағы күн: 1–2 қаңтар, 7 қаңтар, 8 наурыз, 21–23 наурыз, 1 мамыр, 7 мамыр, 9 мамыр, 6 шілде, 30 тамыз, 25 қазан, 16 желтоқсан;
- емтихан сессиясы және семестр соңындағы жоба қорғау аптасы;
- ашық P1 инциденті немесе SLA бұзылған P2 бар кезде.

Тыйымның иесі релиз иесі. Ол басталу және аяқталу күнін арнаға жазады.

| T + 1 сағ | Тапсырыс беруші мен пайдаланушыларға хабарлама жіберіледі (8-бөлім) | Байланыс |
| T + 24 сағ | Релиз issue жабылады, журналға жол қосылады (10-бөлім) | Релиз иесі |

## 5. Релиз чек-парағы

GitHub-та **New issue → Release** шаблоны бар ([`.github/ISSUE_TEMPLATE/release.md`](../.github/ISSUE_TEMPLATE/release.md)). Әр релизде осы тізім сол жерде белгіленеді.

**Релизге дейін**

- [ ] Релизге не кіретіні белгілі: PR тізімі және байланысты тапсырмалар
- [ ] `main`-дегі CI жасыл: ruff, pytest, Trivy, gitleaks, Docker бейнесі
- [ ] Trivy-де HIGH/CRITICAL осалдық жоқ немесе әрқайсысы бойынша шешім бар
- [ ] Стендте қабылданды: негізгі сценарийлер өтті
- [ ] Деректер көшіруі бар болса, ол өнеркәсіптік база көшірмесінде тексерілген
- [ ] `app/main.py` ішіндегі `__version__` тегпен сәйкес
- [ ] Мониторинг пен алерттер жаңа функционалдыққа дайын
- [ ] Терезе тексерілді: тыйым кезеңі емес, кезекші тағайындалған
- [ ] Дерекқордың сақтық көшірмесі жасалды, қалпына келтіру командасы дайын
- [ ] Кері қайтаруға арналған алдыңғы бейненің тегі жазылды

**Релизден кейін**

- [ ] `release.yml` жасыл, GitHub Release жасалды
- [ ] `/health` жаңа нұсқаны қайтарады
- [ ] Smoke-тест: өтінім жасау → «Жұмыста» → «Шешілді»
- [ ] Бірінші сағатта кері қайтару критерийлерінің ешқайсысы орындалмады
- [ ] Тапсырыс берушіге, пайдаланушыларға және қолдауға хабарланды

## 6. Кері қайтару жоспары

### 6.1. Кері қайтару критерийлері

Шешім түнгі үште дауда емес, **алдын ала келісілген цифрлар бойынша** қабылданады. Шығарудан кейінгі 24 сағат ішінде кез келген бір шарт орындалса, кері қайтарамыз:

| # | Критерий | Шек |
|---|---|---|
| 1 | `/health` жауап бермейді | қатарынан 3 тексеру (Uptime Kuma, әр 60 с) |
| 2 | 5xx қателерінің үлесі | 5 минут бойы 2%-дан жоғары |
| 3 | Жауап уақыты p95 | 10 минут бойы 800 мс-тан жоғары (11-дәрістегі мақсатты мән, ФЕТ спецификациясымен салыстырыңыз) |
| 4 | Деректер жоғалды немесе бұрмаланды | кез келген жағдай = P1 |
| 5 | Негізгі сценарий жұмыс істемейді (өтінім жасау, мәртебені өзгерту) | айналып өту жолы жоқ |

Дереккөздер: 1 және 3-критерийлер — Uptime Kuma (11-ЗЖ-да көтеріледі), 2-критерий — контейнер логтары (`docker logs helpdesk`).

Шешімді **релиз иесі** қабылдайды, ол болмаса **кезекші** қабылдайды. Кері қайтару 15 минут ішінде басталуы керек. Алдымен қалпына келтіреміз, себебін кейін іздейміз.

### 6.2. Деректердің сақтық көшірмесі (релизге дейін)

```bash
# контейнер ішіндегі SQLite базасы /data/helpdesk.db
docker cp helpdesk:/data/helpdesk.db backups/helpdesk-$(date +%Y%m%d-%H%M)-before-vX.Y.Z.db
```

### 6.3. Кері қайтару қадамдары

```bash
# 1. Алдыңғы жұмыс істеген нұсқаны анықтау (релиз issue-де жазылған), мысалы 0.1.0
PREV=0.1.0

# 2. Ағымдағы контейнерді тоқтатып, алдыңғы бейнені іске қосу
docker stop helpdesk && docker rm helpdesk
docker pull ghcr.io/southkz0717-source/helpdesk:$PREV
docker run -d --name helpdesk -p 8000:8000 -v helpdesk-data:/data \
  ghcr.io/southkz0717-source/helpdesk:$PREV

# 3. Тексеру: нұсқа алдыңғыға оралды
curl -s http://localhost:8000/health   # {"status":"ok","version":"0.1.0"}
```

**Деректерді қалпына келтіру** тек 4-критерий бойынша (деректер бұзылғанда) жасалады, себебі сақтық көшірмеден кейін жасалған өтінімдер жоғалады:

```bash
docker stop helpdesk
docker cp backups/helpdesk-<уақыты>-before-vX.Y.Z.db helpdesk:/data/helpdesk.db
docker start helpdesk
```

Жоғалған өтінімдердің тізімі тапсырыс берушіге хабарланады.

### 6.4. Деректер көшіруіне арналған ереже

Код оңай қайтарылады, ал дерекқор сұлбасы қиын қайтарылады. Сондықтан сұлба **екі релизбен** өзгереді (expand → contract):

1. Бірінші релиз жаңа баған немесе кесте **қосады**, ескісі жұмыс істей береді. Бұл релизді кері қайтару қауіпсіз.
2. Екінші релиз (кемінде бір аптадан кейін) ескі бағанды **жояды**.

Бір релизде бағанды жою мен оны қолдануды ауыстыруға тыйым салынады.

### 6.5. Кері қайтару чек-парағы

- [ ] Критерий орындалды: қайсысы және қашан (уақыты, графиктің скриншоты)
- [ ] Шешімді қабылдаған адам: релиз иесі / кезекші
- [ ] Арнаға хабарланды: «vX.Y.Z кері қайтарылуда, себебі: …»
- [ ] Алдыңғы бейне іске қосылды, `/health` алдыңғы нұсқаны көрсетеді
- [ ] Smoke-тест өтті
- [ ] Деректер тексерілді; қажет болса, сақтық көшірмеден қалпына келтірілді
- [ ] `incident` белгісі бар issue ашылды (DORA: сәтсіз өзгерістер үлесі мен қалпына келу уақыты)
- [ ] Тапсырыс беруші мен пайдаланушыларға хабарланды
- [ ] 2 жұмыс күні ішінде кінәсіз postmortem өткізілді, әрекеттер бэклогқа енгізілді
- [ ] Бұзылған тег жойылмайды; түзету келесі `Z` нұсқасымен шығады

### 6.6. Кері қайтаруды оқу-жаттығу

Тексерілмеген кері қайтару жұмыс істемейді. Сондықтан әр **үлкен** релизге дейін және кемінде айына бір рет стендте 6.3-бөлім толық жүгіртіледі. Нәтижесі 10-бөлімдегі журналға жазылады: қанша минут кетті және не кедергі жасады.

## 7. Feature flags

Аяқталмаған функционалдық ұзақ өмір сүретін бұтақта емес, жалаушаның артында жасырылады. Жалауша оны жоюға арналған тапсырмамен бірге жасалады. Жалаушалар тізілімі ретроспективада қайта қаралады (10-дәріс). Қазір жобада жалауша жоқ.

## 8. Релиз туралы хабарламалар

| Кімге | Қашан | Не айтылады |
|---|---|---|
| Тапсырыс берушіге | T + 1 сағ | Тапсырмалар тізімі емес, пайдасы: «Енді өтінімдерді тақырып бойынша іздеуге болады» |
| Пайдаланушыларға | T + 1 сағ | Не өзгерді, бірдеңе дұрыс жұмыс істемесе не істеу керек |
| Қолдауға | **T − 1 күн** | Не өзгереді, қандай сұрақтар келуі мүмкін |
| Команда арнасына | T, T + 15 мин, T + 1 сағ | Шығару статусы (жеке хатта емес) |

Шаблон: *«Helpdesk vX.Y.Z шықты. Не жаңа: … . Бір нәрсе дұрыс жұмыс істемесе, P1/P2 өтінімін ашыңыз немесе кезекшіге жазыңыз: …»*

Релизден кейін үнсіз қалуға болмайды: үнсіздік «бірдеңе дұрыс болмады» деп оқылады.

## 9. Инциденттерді тіркеу

Продакшендегі P1/P2 ақау GitHub-та **New issue → Incident** шаблоны арқылы ашылады ([`.github/ISSUE_TEMPLATE/incident.md`](../.github/ISSUE_TEMPLATE/incident.md)). Шаблон `incident` белгісін өзі қояды. Түзету шыққанда issue жабылады. Осы деректерден [`scripts/dora.py`](../scripts/dora.py) сәтсіз өзгерістер үлесін және қалпына келу уақытын есептейді.
