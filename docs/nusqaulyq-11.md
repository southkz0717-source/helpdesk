## 1. 11-ЗЖ не туралы

ЗС 10 кодты **қалай жеткізу** керек екені туралы болды. 11-ЗЖ — жеткізілген нәрсенің **сапасы**, оны тапсырыс берушінің **қабылдауы** және оны **пайдалану** туралы.

Лекцияның негізгі ойлары:

- Сапаны тестілеушілер жасамайды, олар бар нәрсені өлшейді. Сапа ертерек қабылданған шешімдермен жасалады.
- Ақаудың құны продакшенге жақындаған сайын **реттермен** өседі: талаптарда 1, продакшенде 50–100.
- UAT — демонстрация емес және тілек жинау емес: келісілген сценарийлер бойынша **тапсырыс беруші жұмыс істейді**.
- Postmortem кінәлі іздемейді. Сұрақ: «бұл әрекет неге дұрыс болып көрінді?».
- Runbook оқып шығумен емес, **жүгіртумен** тексеріледі.

## 3. Не орнату керек

Негізгі нұсқаулықтағы 2–3-бөлімдерге қосымша (Python, Git, виртуалды орта):

```powershell
pip install -r requirements-dev.txt -r requirements-e2e.txt -r requirements-load.txt
python -m playwright install chromium
```

| Файл | Не орнатады | Не үшін |
|---|---|---|
| `requirements-dev.txt` | pytest, ruff, httpx, matplotlib | Модульдік және API тесттері, линтер, DORA |
| `requirements-e2e.txt` | Playwright, pytest-playwright | Браузердегі E2E тесттері |
| `requirements-load.txt` | Locust | Жүктеме тесті |
| `playwright install chromium` | Chromium браузері (~150 МБ) | Playwright тесттерді осы браузерде жүргізеді |

**Docker Desktop** демо-стенд пен Uptime Kuma үшін керек (5-бөлім).

## 4. Барлық тесттерді іске қосу

### 4.1. Модульдік және API тесттері

```powershell
pytest
```

Күтілетін нәтиже: `55 passed`. Бұл — пирамиданың төменгі екі деңгейі:

| Деңгей | Файлдар | Саны |
|---|---|---|
| Модульдік | `test_sla`, `test_timefmt`, `test_anonymize`, `test_storage`, `test_dora`, `test_seed` | 31 |
| API / интеграциялық | `test_api` | 24 |

### 4.2. E2E тесттері (нақты браузерде)

```powershell
pytest e2e
```

Күтілетін нәтиже: `6 passed`. Тест сервисті өзі іске қосады, Chromium ашады және пайдаланушы сияқты әрекет етеді.

Браузерді **көзбен көру** үшін (мұғалімге көрсету үшін ыңғайлы):

```powershell
pytest e2e --headed --slowmo 500
```

`--headed` браузер терезесін көрсетеді, `--slowmo 500` әр әрекеттің арасында 0,5 секунд күтеді.

| E2E тест | Қай UAT сценарийі |
|---|---|
| `test_create_ticket_and_see_sla` | UAT-01: студент өтінім береді, SLA мерзімдерін көреді |
| `test_full_status_lifecycle` | UAT-02: оператор өтінімді жұмысқа алып, жабады |
| `test_language_switch` | UAT-06: үш тілде жұмыс |
| `test_search_ignores_case_in_kazakh` | UAT-04: қазақша бас әріппен іздеу |
| `test_required_fields_block_submit` | UAT-01 теріс сценарийі: бос форма жіберілмейді |
| `test_form_is_usable_from_keyboard` | UAT-09: тек пернетақтамен толтыру (қолжетімділік) |

### 4.3. Жүктеме тесті (Locust)

Бірінші терминалда сервис:

```powershell
uvicorn app.main:app --port 8000
```

Екінші терминалда жүктеме (200 пайдаланушы, 2 минут):

```powershell
locust -f loadtest/locustfile.py --host http://127.0.0.1:8000 --headless -u 200 -r 20 -t 2m --html loadtest/report.html
```

Соңында мына жол шығады:

```
TARGET p95 < 800 ms: 81 ms | errors < 1%: 0.01% -> PASS
```

`loadtest/report.html` файлын браузерде ашыңыз: графиктер, жауап уақыты, қателер.

> `--headless` жоқ болса, Locust веб-интерфейсін ашады: http://localhost:8089. Онда жүктемені тікелей өсіріп, графиктерді нақты уақытта көрсетуге болады. Мұғалімге көрсетуге әсерлі.

### 4.4. Тест деректерін иесіздендіру

```powershell
$env:ANONYMIZE_KEY = "кез-келген-құпия"
python scripts/anonymize.py helpdesk.db stand.db
```

`helpdesk.db` — өнеркәсіптік база (мысал ретінде — сіздің локалды базаңыз), `stand.db` — стендке арналған көшірме.
Нәтижесін тексеру:

```powershell
python -c "import sqlite3; [print(r) for r in sqlite3.connect('stand.db').execute('select requester, description from tickets limit 3')]"
```

Аттардың орнында `Пайдаланушы-0427`, ал e-mail мен телефонның орнында `[email]`, `[phone]` тұрады.

## 5. Демо-стенд: Docker + Uptime Kuma

### 5.1. Іске қосу

```powershell
docker compose --profile monitoring up -d
```

| Сервис | Мекенжай | Не |
|---|---|---|
| Helpdesk | http://localhost:8000 | Соңғы релиз (`latest`), деректер атаулы томда |
| Uptime Kuma | http://localhost:3001 | Мониторинг |

> **Порттар бос емес болса** (компьютерде басқа жоба 8000 немесе 3001 портын алып тұрса):
> ```powershell
> $env:HELPDESK_PORT = "8090"; $env:KUMA_PORT = "3002"
> docker compose --profile monitoring up -d
> ```
> Содан кейін http://localhost:8090 және http://localhost:3002 ашыңыз.

### 5.2. Стендті деректермен толтыру

```powershell
python -m scripts.seed --url http://127.0.0.1:8000 --count 200
```

200 шынайы синтетикалық өтінім: әртүрлі басымдықтар, мәртебелер, қазақша және орысша тақырыптар.

### 5.3. Uptime Kuma мониторын баптау

1. http://localhost:3001 ашыңыз → әкімші аккаунтын жасаңыз (тек өз компьютеріңізде).
2. **Add New Monitor**:

   | Өріс | Мәні |
   |---|---|
   | Monitor Type | **HTTP(s) - Keyword** |
   | Friendly Name | Helpdesk health |
   | URL | `http://helpdesk:8000/health` |
   | Keyword | `"persistent_storage":true` |
   | Heartbeat Interval | 60 |
   | Retries | 3 |

3. **Save**. Монитор жасыл болуы керек.

URL-да `localhost` емес, `helpdesk` жазылады: Uptime Kuma сол Docker желісінде, ол Helpdesk-ті сервис атымен табады. Порт әрқашан контейнер ішіндегі 8000.

**Неге кілт сөз `persistent_storage`:** монитор екі жағдайда алерт береді — сервис жауап бермесе **және** ол томсыз іске қосылса. Екінші жағдай — #7 инциденті, мұнда ол мониторингке айналды (postmortem-дегі A2 әрекеті, issue #14).

### 5.4. Тоқтату

```powershell
docker compose --profile monitoring stop
```

Деректер томдарда сақталады. `docker compose down -v` **томдарды да жояды** — оны тек стендті толық тазалау керек болғанда ғана қолданыңыз.

## 6. UAT-ты басқа командамен өткізу

Бұл — **тек сіз** орындай алатын тапсырма: «тапсырыс беруші» рөлін басқа команда атқарады.

### Дайындық (UAT-тан 1–2 күн бұрын)

- [ ] Көрші командамен келісіңіз: кім кімге және қашан UAT өткізеді (60 минут).
- [ ] Оларға [uat.md](uat.md) сілтемесін жіберіңіз. Сценарийлер **алдын ала** келісіледі, UAT күні бірінші рет көрсетілмейді.
- [ ] Белгілер бар екенін тексеріңіз (**Issues → Labels**): `uat`, `bug`, `clarification`, `change-request`.

### UAT күні

1. **30 минут бұрын:** стендті көтеріңіз (5-бөлім), `/health` → `"version":"0.4.0"`, `"persistent_storage":true`. Өтінімдер саны 200-ден кем болмауы керек.
2. **[uat-protocol.md](uat-protocol.md)** шаблонын көшіріңіз: `docs/uat-protocol-2026-11-ДД.md`. 1-бөлімін толтырыңыз.
3. **15 минут оқыту:** интерфейс, тілдер, ескертуді қалай жазу керек. Интерфейсті білмеу ақау ретінде жазылмауы керек.
4. **Олар сценарийлерді өздері орындайды.** Сіз тек бақылайсыз және жазасыз. Түймені олардың орнына баспаңыз — бұл демонстрация емес.
5. **Әр сценарийден кейін** хаттамада «Өтті / Өтпеді» белгілеңіз.
6. **Әр ескерту:** **Issues → New issue → UAT remark** → тапсырыс берушінің қасында **бірден** топқа бөліңіз:

   | Топ | Белгі | Мысал |
   |---|---|---|
   | Ақау | `bug` | «P2-нің шешу мерзімі 2 күн емес, 3 күн көрсетілді» |
   | Талапты нақтылау | `clarification` | «Мерзім жұмыс күндерімен бе, күнтізбелік күндермен бе?» |
   | Өзгеріс сұранысы | `change-request` | «Өтінімге файл тіркеу керек» |

   Өзгеріс сұранысына «жоқ» демеңіз: «Иә, және бұл мынаны өзгертеді: +N күн, оның орнына X кейінге қалады».
7. **Шешім** (uat.md, 7-бөлім): қабылданды / ескертулермен қабылданды / қабылданбады.
8. Тапсырыс берушінің өкілі хаттамаға қол қояды.

### UAT-тан кейін

Хаттаманы PR ретінде қосыңыз: жаңа бұтақ → `docs/uat-protocol-2026-11-ДД.md` → PR. Тапсырыс берушінің өкілі PR-да **Approve** басады немесе «Қабылдаймын» деп жазады — бұл электронды «қол».

## 8. Мұғалімге көрсету сценарийі (10–15 минут)

Алдын ала ашып қойыңыз: репозиторий, `docs/test-strategy.md`, `docs/postmortem-7.md`, `docs/runbook-restore.md`, `loadtest/results/before-v0.3.1.html` және `after-v0.4.0.html`, демо-стенд.

### 0. Кіріспе (30 секунд)

> «11-ЗЖ-да мен Helpdesk-тің сапасын өлшеуді, тапсырыс берушінің қабылдауын және пайдалануды бірінші күннен бастап жоспарладым.
> Ең маңызды нәтиже: тесттер бірнеше нақты ақауды тапты, ал runbook-ты нақты жүгірткенде оның өзінен 4 қате шықты.»

### 1. Тестілеу стратегиясы (4 минут)

1. **`docs/test-strategy.md`**, 1-бөлім — пирамида:
   > «Төменде 31 модульдік және 24 API тесті (жылдам, секундтар), жоғарыда 6 E2E (баяу). Пирамида төңкерілмеген: E2E тек негізгі сценарийлерді жабады.»
2. **Тікелей көрсету:** терминалда `pytest e2e --headed --slowmo 500` — браузер өзі өтінім береді, мәртебелерді ауыстырады, тілдерді өзгертеді.
3. **Жүктеме тесті** — ең мықты дәлел. Екі есепті қатар ашыңыз:

   | | v0.3.1 | v0.4.0 |
   |---|---|---|
   | p95 | 4000 мс ❌ | 81 мс ✅ |
   | HTTP 500 | 53 (`database is locked`) | 0 |

   > «Тапсырма "өнімділікті тексеру" емес: профиль, нысана p95 < 800 мс және 2 минут. Тест екі ақау тапты: SQLite бұғаттаулары және беттеудің жоқтығы. WAL мен беттеу қосылды, нәтиже 50 есе жақсарды.»
4. **Иесіздендіру:** `scripts/anonymize.py` ашып, айтыңыз:
   > «Аттар жай өшірілмейді, **ауыстырылады**: бір адам әрқашан бір бүркеншік ат алады. E-mail, телефон, ЖСН, карта нөмірі маскаланады. Тест стенд файлының байттарында дербес деректердің мүлде жоқтығын тексереді.»
5. **Uptime Kuma** (стенд көтерілген болса): мониторды көрсетіңіз және кілт сөздің `persistent_storage` екенін айтыңыз.

### 2. UAT (3 минут)

1. **`docs/uat.md`**, 6-бөлім:
   > «Сценарийлер жүйе функцияларының тілінде емес, пайдаланушы жұмысының тілінде жазылған: "Студент принтердің бұзылғаны туралы хабарлайды", ал "өтінім формасын тексеру" емес.»
2. Бір сценарийді көрсетіңіз (мысалы, UAT-04): **өлшенетін** өту критерийі — «200+ өтінімде нәтиже 1 секундтан тез».
3. **5-бөлім** — ескертулерді сұрыптау: ақау / нақтылау / өзгеріс сұранысы.
4. **Толтырылған хаттама** (UAT өткізілгеннен кейін) және `uat` белгісі бар issue-лер.

### 3. Postmortem (3 минут)

**`docs/postmortem-7.md`** ашыңыз:

1. Басындағы ескерту: *«Бұл талдау кінәлі іздемейді»*.
2. **4.1-бөлім** — «Бұл шешімдер неге дұрыс болып көрінді». Мысалы: `docker run -p 8000:8000` — Docker-дің ең таныс командасы, ақау тек екінші контейнерде көрінеді.
3. **4.2-бөлім** — 5 жүйелік фактор. Айтыңыз: *«Себеп бір адамның қатесі емес, жүйелік факторлардың тоғысуы»*.
4. **4.3-бөлім** — «Не жұмыс істеді» (міндетті бөлім).
5. **5-бөлім** — 3 әрекет → **Issues → #13, #14, #15** ашып көрсетіңіз: иесі, мерзімі, орындалу белгісі.
   > «"Мұқият болу" — әрекет емес. "CI-ге upgrade-test job қосу" — әрекет.»

### 4. Runbook (3 минут)

**`docs/runbook-restore.md`** ашыңыз:

1. Әр қадамда **нақты команда** және **күтілетін нәтиже** бар, «сервис күйін тексеріңіз» сияқты жалпы сөздер жоқ.
2. **5-бөлім** — «Көмектеспесе не істеу керек», эскалация.
3. **6-бөлім — жаттығулар журналы**, ең маңызды бөлім:
   > «Runbook-ты стендте нақты жүгірттім: 200 өтінімнің 150-і жойылды, қалғаны бұзылды. Runbook бойынша 200-і де қалпына келтірілді, нысана RTO 15 минут орындалды.
   > Ең бастысы: жаттығу **runbook-тың өзінен 4 қате** тапты, мысалы бұзылған көшірме тізімнің басында тұрады — түнгі үште оны қателесіп қалпына келтіру оңай. Тексерілмеген нұсқаулық әдетте жұмыс істемейді.»

### Қорытынды сөз (30 секунд)

> «Барлық 5 тапсырма орындалды. Postmortem кінәлі іздемейді, әрекеттер нақты және бэклогта.
> Негізгі тұжырым: әр тексеру — жүктеме тесті, UAT сценарийлері, runbook жаттығуы — бір нақты әлсіз жерді тапты. Сапа соңында емес, процестің әр сатысында өлшенді.»

## 10. Мұғалім қоюы мүмкін сұрақтар

**— UAT-ты кім өткізді?**
[Көрші команданың атауы] «тапсырыс беруші» рөлінде, сценарийлерді өздері орындады. Хаттама — `docs/uat-protocol-…md`, ескертулер — `uat` белгісі бар issue-лер.

**— Неге E2E тесттер тек 6?**
Пирамида бойынша: E2E баяу және сынғыш, сондықтан тек негізгі сценарийлерді жабады. Логиканың қалған бөлігі 55 модульдік және API тестімен тексеріледі.

**— Жүктеме тесті ноутбукте жүрді — нәтиже сенімді ме?**
Жоқ, абсолютті мән ретінде емес. Ол **салыстырмалы**: түзетуге дейін және кейін, бір жағдайда. Бұл стратегияда (6-бөлім) ашық жазылған. Бірақ табылған ақаулар (бұғаттаулар, беттеудің жоқтығы) нақты.

**— Неге продакшен базасының көшірмесін жай қолданбадыңыздар?**
Лекция бойынша, бұл — дербес деректердің ағып кетуінің ең жиі себебі. Стендке тек `anonymize.py` арқылы иесіздендірілген көшірме түседі.

**— Postmortem-де неге кінәлі жоқ, ақауды біреу жасады ғой?**
Бастапқы жорамал: адам сол сәтте білгеніне сүйеніп, саналы әрекет етті. README-дегі команда стандартты болатын. Себеп — тексерудің жоқтығы (F1), екі нұсқаулықтың қайшылығы (F2) және т.б. Кінәлі іздей бастасақ, келесі инцидентті жасыратын болады.

**— Әрекеттер орындалды ма?**
Олар бэклогта (#13–#15), иесі мен мерзімі бар. Орындалуы қадағаланады: орындалмаған әрекеттер келесі талдауда тексеріледі.

**— Runbook жұмыс істейтінін қайдан білесіз?**
Оны стендте нақты жүгірттім (6-бөлім, журнал): 200 → 50 → 200 өтінім. Сонымен қатар жаттығу runbook-тың өзінен 4 қате тапты, олар түзетілді.

**— RPO 24 сағат — бұл қайдан?**
Нысана: көшірме әр релизден бұрын және күн сайын жасалады. Ең нашар жағдайда соңғы көшірмеден кейінгі тәуліктің деректері жоғалады.

## 11. Жиі кездесетін қателер

| Қате | Себебі | Шешімі |
|---|---|---|
| `pytest e2e` → `Executable doesn't exist ... chromium` | Браузер орнатылмаған | `python -m playwright install chromium` |
| `docker compose up` → `port is already allocated` | Басқа жоба 8000 немесе 3001 портын алып тұр | `$env:HELPDESK_PORT="8090"; $env:KUMA_PORT="3002"` (5.1-бөлім) |
| Seed скрипті немесе сұраныстар **өте баяу** | Windows-та `localhost` алдымен IPv6-ны байқап көреді: әр қосылымға ~2 с | `localhost` орнына `127.0.0.1` жазыңыз |
| `python scripts/seed.py` → `No module named 'app'` | Скрипт модуль ретінде іске қосылуы керек | `python -m scripts.seed ...` |
| Uptime Kuma: монитор қызыл, `ECONNREFUSED` | URL-да `localhost` жазылған | `http://helpdesk:8000/health` (контейнер аты және ішкі порт) |
| Locust → `FAIL` | Нысана орындалмады — бұл тесттің нәтижесі, қате емес | Есептен қай сұраныс баяу екенін қараңыз |
| `anonymize.py` → `already exists, refusing to overwrite` | Мақсатты файл бар | Басқа атау беріңіз немесе ескі файлды өшіріңіз |
| `docker compose down -v` кейін өтінімдер жоқ | `-v` томдарды да жояды | Тек `stop` немесе `down` (`-v`-сыз) қолданыңыз. Деректер жоғалса — runbook RB-01 |
