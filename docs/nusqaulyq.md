## 1. Жоба туралы қысқаша

**Helpdesk** — техникалық қолдау қызметіне өтінімдер беретін веб-сервис.

- Пайдаланушы өтінім жасайды: тақырып, өтініш беруші, басымдық (P1–P4), сипаттама.
- Сервис басымдыққа қарай **SLA мерзімдерін** өзі есептейді: қашан жауап беру керек және қашан шешу керек.
- Өтінім мәртебелері: `Жаңа → Жұмыста → Шешілді → Жабылды`.
- Интерфейс үш тілде: қазақша, орысша, ағылшынша.
- Өтінімдерді тақырып, өтініш беруші немесе сипаттама бойынша іздеуге болады.

| Басымдық | Не | Жауап | Шешу |
|---|---|---|---|
| P1 — сыни | Жүйе қолжетімсіз, деректер жоғалды | 15 минут | 8 сағат |
| P2 — жоғары | Негізгі сценарий жұмыс істемейді | 2 сағат | 2 күн |
| P3 — орташа | Ыңғайсыздық, айналып өту жолы бар | 1 күн | 14 күн |
| P4 — төмен | Косметика | міндеттеме жоқ | міндеттеме жоқ |

**Технологиялар:** Python 3.13, FastAPI (веб-фреймворк), SQLite (дерекқор), Jinja2 (HTML шаблондары).

**ЗС 10 не туралы:** қосымшаның өзі емес, оны **жеткізу процесі** маңызды:
автоматты тексерулер (CI/CD), `main` бұтағын қорғау, DORA метрикалары және релиз жоспары.

## 3. MVP-ді компьютерде іске қосу

> **Маңызды (Windows):** жобаны **қысқа жолға** қойыңыз, мысалы `C:\dev\helpdesk`.
> Жол тым ұзын болса (мысалы, `C:\Users\...\Desktop\...\...`), Windows 260 таңбадан ұзын жолдарды
> қолдамайды және кітапханаларды орнату қатемен аяқталады.

**1-қадам. Кодты жүктеу**

```powershell
mkdir C:\dev
cd C:\dev
git clone https://github.com/southkz0717-source/helpdesk.git
cd helpdesk
```

**2-қадам. Виртуалды орта жасау**

Виртуалды орта (venv) — осы жобаға арналған жеке Python «қорабы». Кітапханалар жүйеге емес, осында орнатылады.

```powershell
python -m venv .venv
.venv\Scripts\activate
```

Жолдың басында `(.venv)` пайда болуы керек.

> PowerShell «running scripts is disabled» деп қате берсе, бір рет орындаңыз:
> `Set-ExecutionPolicy -Scope CurrentUser RemoteSigned`, содан кейін `activate`-ті қайталаңыз.

**3-қадам. Кітапханаларды орнату**

```powershell
pip install -r requirements-dev.txt
```

`requirements.txt` — қосымшаға керек кітапханалар. `requirements-dev.txt` — оларға қоса тесттер, линтер және DORA скрипті.

**4-қадам. Сервисті іске қосу**

```powershell
uvicorn app.main:app --reload
```

`Uvicorn running on http://127.0.0.1:8000` деген жол шықса, сервис жұмыс істеп тұр.
`--reload` — кодты өзгерткенде сервер өзі қайта іске қосылады.

**5-қадам. Браузерде ашу**

| Мекенжай | Не көрсетеді |
|---|---|
| http://localhost:8000 | Басты бет: жаңа өтінім формасы және өтінімдер тізімі |
| http://localhost:8000/?lang=ru | Сол бет орысша (`kk`, `ru`, `en`) |
| http://localhost:8000/docs | API құжаттамасы (Swagger): барлық эндпоинттерді осы жерден тексеруге болады |
| http://localhost:8000/health | Сервис күйі: `{"status":"ok","version":"0.3.1",...}` |

Тоқтату: терминалда **Ctrl + C**.

## 4. Қосымшада не тексеру керек

Бұл — қысқа демо, оны мұғалімге де көрсетуге болады.

1. **Өтінім жасау.** Тақырып: `Принтер 305 аудиторияда басып шығармайды`, өтініш беруші: `Айгерім`, басымдық: `P2` → **Жіберу**.
   Өтінім беті ашылады: **жауап мерзімі** = құрылған уақыт + 2 сағат, **шешу мерзімі** = + 2 күн.
   Уақыт Алматы бойынша көрсетіледі (`UTC+5`).
2. **Мәртебені өзгерту.** «Мәртебені өзгерту» → `Жұмыста` → `Шешілді` → `Жабылды`.
   Рұқсат етілмеген өтуге (мысалы, `Жаңа` → `Жабылды`) жүйе жол бермейді.
3. **Тілді ауыстыру.** Жоғарғы оң жақтағы `KK / RU / EN`.
4. **Іздеу.** Басты бетте іздеу жолына `ПРИНТЕР` деп бас әріппен жазыңыз — өтінім бәрібір табылады.
   Іздеу қазақ және орыс әріптерінде регистрге тәуелсіз.
5. **API.** http://localhost:8000/docs → `GET /api/stats` → **Try it out** → **Execute**:
   ашық өтінімдер басымдықтар бойынша және SLA бұзылған өтінімдер саны.

## 6. Docker арқылы іске қосу (міндетті емес)

Docker Desktop орнатылып, іске қосылған болуы керек.

```powershell
docker compose up -d
```

Бұл GitHub Container Registry-ден соңғы релиздің дайын бейнесін жүктеп, оны **атаулы томмен** іске қосады.

```powershell
docker compose ps                                       # контейнер жұмыс істеп тұр ма
$env:HELPDESK_VERSION="0.3.0"; docker compose up -d     # нақты нұсқаға ауысу (кері қайтару)
Remove-Item Env:HELPDESK_VERSION; docker compose up -d  # соңғы нұсқаға оралу
docker compose down                                     # тоқтату (деректер томда сақталады)
```

> Linux/macOS терминалында: `HELPDESK_VERSION=0.3.0 docker compose up -d`.
> Бейнелер жария: GitHub аккаунтынсыз да жүктеледі.

**Том (volume) неге маңызды:** өтінімдер контейнер ішіндегі `/data/helpdesk.db` файлында сақталады.
Томсыз контейнерді жойып, жаңасын іске қосқанда барлық өтінім жоғалады. Бұл **#7 инцидент** болды (8-бөлімді қараңыз).
Тексеру: http://localhost:8000/health → `"persistent_storage": true`.

## 8. Мұғалімге көрсету сценарийі (10–15 минут)

Алдын ала ашып қойыңыз: репозиторий беті, Actions, Releases, `docs/dora-analysis.md`, қосымша (`localhost:8000`).

### 0. Кіріспе (1 минут)

Айтатын сөз:
> «Жоба — Helpdesk, P1–P4 басымдықтары мен SLA мерзімдері бар қолдау қызметі.
> ЗС 10-да мен оның жеткізу процесін құрдым: CI/CD құбыржолы, бұтақты қорғау,
> нақты деректер бойынша DORA дашборды және релиз жоспары.»

Қысқаша қосымшаны көрсетіңіз: өтінім жасау, тілді ауыстыру, іздеу (4-бөлім).

### 1. Құбыржол — 1-тапсырма (3 минут)

1. **Code → `.github/workflows/ci.yml`** ашыңыз да, job-тарды атаңыз:

   | Job | Не істейді |
   |---|---|
   | Lint (ruff) | Линтер мен пішімдеу |
   | Tests (pytest) | 40 автотест |
   | Security (Trivy, gitleaks) | Тәуелділіктердегі осалдықтар және кодтағы құпиялар |
   | Build and publish image | Docker бейнесін құрастыру, `/health` smoke-тесті, бейнені Trivy-мен тексеру, артефакт, `main`-де GHCR-ге жариялау |

2. **Actions → CI** — жасыл іске қосуды ашыңыз: төрт job-тың бәрі ✅, төменде **Artifacts**.
3. **Ең мықты дәлел:** **Actions → CI → #1 және #2** — қызыл іске қосулар. Айтыңыз:
   > «Құбыржол шын қатені ұстады: Trivy `python-multipart 0.0.20` кітапханасынан 3 HIGH осалдық тапты
   > (CVE-2026-24486, -42561, -53539). Мен тексеруді өшірмедім, кітапхананы 0.0.34-ке жаңарттым.»

   Бұл PR #1-дің коммиттерінде де көрінеді.

### 2. Бұтақты қорғау — 2-тапсырма (2 минут)

1. **Settings → Rules → Rulesets** → ережені ашыңыз. Көрсетіңіз:
   - Require a pull request before merging
   - Require status checks to pass + 4 тексеру
   - Block force pushes, Restrict deletions
2. Айтыңыз: *«Required approvals = 0, өйткені командада бір адам: GitHub авторға өз PR-ын бекітуге рұқсат бермейді.
   Команда болса, 1 қоямыз.»*
3. **Тікелей көрсету** (міндетті емес, бірақ әсерлі). Терминалда:

   ```powershell
   git commit --allow-empty -m "test: direct push"
   git push origin main
   ```

   GitHub бас тартады: `Changes must be made through a pull request` және `4 of 4 required status checks are expected`.
   Содан кейін бос коммитті жойыңыз: `git reset --hard origin/main`.

### 3. DORA дашборды — 3-тапсырма (3 минут)

1. **`docs/dora/dashboard.png`** ашыңыз — төрт график.
2. **`docs/dora.md`** — метрикалар қалай анықталады:
   - **жаю** = GitHub Release (`vX.Y.Z` тегі);
   - **инцидент** = `incident` белгісі бар issue.
3. **Тікелей есептеу:** **Actions → DORA dashboard → Run workflow → Run workflow**.
   *Қорғауға дейін бір рет алдын ала іске қосып көріңіз* — сонда жасыл нәтиже дайын тұрады.
   ~30 секундтан кейін іске қосуды ашыңыз: **Summary**-де метрикалар кестесі, төменде **Artifacts → `dora-dashboard`**.
   Айтыңыз: *«Деректер GitHub API арқылы репозиторийдің нақты тарихынан жиналады, ақылы BI жоқ.»*

### 4. Деңгейлер және жақсартулар — 4-тапсырма (3 минут)

**`docs/dora-analysis.md`** ашыңыз.

| Метрика | Мәні | Деңгей | Айтатын түсіндірме |
|---|---|---|---|
| Жаю жиілігі | 4 / апта | High | 4 релиз 1,5 сағатқа сыйды — шын ырғақ емес, оқу кестесі |
| Коммиттен продқа | 17 мин | Elite | Сол себеп: терезелермен 1–3 күн болады |
| Сәтсіз өзгерістер үлесі | 25% | **Low** | **Ең сенімді сигнал:** P1 ақауы барлық тексерулерден өтіп кетті |
| Қалпына келу | 4 мин | Elite | Шамадан тыс жақсы: issue мерж кезінде жабылды, табу уақыты тіркелмеді |

**#7 инциденті** туралы (**Issues → #7**, **Pull requests → #8**):
> «README бойынша контейнер томсыз іске қосылатын. Әр жаңартуда барлық өтінімдер жоғалатын — бұл P1.
> v0.3.1-де түзеттік: `VOLUME /data`, `docker-compose.yml` томмен, `/health`-та `persistent_storage`.»

**Екі жақсарту:**
1. **CI-ге жаңарту тесті:** ескі нұсқаны томмен іске қосып, өтінімдер жасап, жаңа нұсқаға ауысып, өтінімдер сақталғанын тексеру.
   Әсері: #7 сияқты ақаулар релизге дейін ұсталады. Мақсат — сәтсіз өзгерістер үлесі ≤ 15%, кейін ≤ 10%.
2. **Мониторинг және инцидент процесі:** Uptime Kuma `/health`-ты тексереді, `Fix #N` орнына `Refs #N`,
   инцидент тек релизден кейін жабылады. Әсері: қалпына келу уақыты шынайы өлшенеді, ақау минуттарда табылады.

### 5. Релиз жоспары — 5-тапсырма (2 минут)

**`docs/release-plan.md`** ашыңыз және бөлімдерді атаңыз:

- **Кері қайтару командалары:** алдыңғы бейнені GHCR-ден іске қосу, дерекқорды сақтық көшірмеден қалпына келтіру.
- **Релиз журналы (10-бөлім):** барлық релиздер, оның ішінде **терезеден тыс** шыққандары — жасырмай белгіленген.

## 9. Терминдер сөздігі

**Процесс және GitHub**

| Термин | Мағынасы |
|---|---|
| **Репозиторий** | Жобаның барлық коды мен тарихы сақталатын орын |
| **Бұтақ (branch)** | Кодтың жеке нұсқасы. `main` — негізгі бұтақ, қалғандары жұмыс бұтақтары (`feat/search`, `fix/data-volume`) |
| **Коммит** | Сақталған өзгеріс: не, кім, қашан өзгертті |
| **Pull request (PR)** | Жұмыс бұтағын `main`-ге біріктіру туралы сұраныс. Бұл жерде ревью және CI тексерулері өтеді |
| **Мерж (merge)** | PR-ды `main`-ге біріктіру. **Create a merge commit** коммиттердің шын уақытын сақтайды (DORA үшін маңызды) |
| **Ревью** | Басқа адамның кодты мерждің алдында қарауы |
| **Бұтақты қорғау / Ruleset** | `main`-ге тікелей push-қа тыйым: тек PR арқылы және тексерулер жасыл болғанда |
| **Issue** | Тапсырма, ақау немесе инцидент жазбасы |
| **Белгі (label)** | Issue-ге қойылатын тег, мысалы `incident`, `release` |
| **Тег (tag)** | Белгілі бір коммитке қойылған ат, мысалы `v0.3.1` |
| **Релиз** | Тегке байланған жарияланған нұсқа (GitHub Releases) |
| **SemVer** | `X.Y.Z` нұсқалау: X — үйлесімсіз өзгеріс, Y — жаңа функция, Z — түзету |

**CI/CD**

| Термин | Мағынасы |
|---|---|
| **CI** (Continuous Integration) | Әр өзгерісте кодты автоматты тексеру: линтер, тесттер, қауіпсіздік |
| **CD** (Continuous Delivery) | Тексерілген кодты автоматты құрастыру және жариялау |
| **Құбыржол (pipeline)** | Тексерулер мен құрастыру қадамдарының тізбегі |
| **GitHub Actions** | Құбыржолдарды GitHub серверлерінде іске қосатын қызмет |
| **Workflow** | Бір құбыржолдың сипаттамасы (`.github/workflows/*.yml` файлы) |
| **Job** | Workflow ішіндегі жеке тапсырма (Lint, Tests, Security, Build) |
| **Линтер (ruff)** | Кодты іске қоспай қателер мен стиль бұзушылықтарын табатын құрал |
| **pytest** | Python-дағы автотесттерді іске қосатын құрал |
| **Trivy** | Тәуелділіктер мен Docker бейнесіндегі белгілі осалдықтарды іздейтін сканер |
| **CVE** | Белгілі осалдықтың халықаралық нөмірі, мысалы CVE-2026-24486 |
| **gitleaks** | Кодта құпиялардың (парольдер, токендер) жоқтығын тексереді |

| **Docker бейнесі (image)** | Қосымша мен оның барлық тәуелділігі бар дайын «пакет» |

| **Том (volume)** | Контейнерден тыс сақталатын деректер — контейнер жойылса да қалады |
| **GHCR** | GitHub Container Registry — Docker бейнелерін сақтайтын орын |
| **Smoke-тест** | Ең негізгі функциялардың жұмыс істейтінін жылдам тексеру (`/health`, өтінім жасау) |

**DORA және релиздер**

| Термин | Мағынасы |
|---|---|
| **DORA** | Google зерттеу тобы ұсынған жеткізудің 4 метрикасы |

## 10. Мұғалім қоюы мүмкін сұрақтар

**— Неге барлық релиздер бір күнде шықты? Бұл терезелерге қайшы емес пе?**
Иә, бұл релиз жоспарынан ауытқу және ол [релиз журналында](release-plan.md#10-релиз-журналы) ашық тіркелген.
Себебі — оқу жобасының мерзімі. Сондықтан жылдамдық метрикалары шамадан тыс жақсы, бұл талдауда жазылған.

**— Неге сәтсіз өзгерістер үлесі Low?**
4 релиздің біреуі P1 инцидентіне әкелді — 25%. Деректер аз болса да, бұл нақты сигнал:
жаңартуды тексеретін тест жоқ. Бірінші жақсарту дәл соған бағытталған.

**— Жаю дегеніміз не, сізде продакшен жоқ қой?**
Жобада жаю = GitHub Release: тег → тесттер → GHCR-ге бейне → релиз. Бейнені кез келген сервер
`docker compose up -d` арқылы іске қоса алады. Бұл анықтама `docs/dora.md`-да бекітілген.

**— Құбыржолдың пайдасы неде?**
Ол шын осалдықты ұстады (python-multipart, 3 HIGH) және қате кодты `main`-ге жібермейді:
бұтақты қорғау 4 тексерудің жасыл болуын талап етеді.

**— Required approvals неге 0?**
Командада бір адам. GitHub авторға өз PR-ын бекітуге рұқсат бермейді, 1 қойсақ ешнәрсені мерждей алмаймыз.

**— Кері қайтаруды қалай жасайсыз?**
`HELPDESK_VERSION=0.3.0 docker compose up -d` немесе `release-plan.md` 6.3-бөліміндегі командалар.
Шешім алдын ала келісілген цифрлар бойынша қабылданады, мысалы `/health` қатарынан 3 рет жауап бермесе.

**— Неге инцидентте кері қайтару жасалмады?**
Ақау кодта емес, жаю нұсқаулығында болды (томсыз іске қосу). Алдыңғы нұсқаға оралу көмектеспес еді,
сондықтан түзету жаңа нұсқамен (v0.3.1) шықты.

## 11. Жиі кездесетін қателер

| Қате | Себебі | Шешімі |
|---|---|---|
| `pip install` кезінде `No such file or directory` немесе `ensurepip` қатесі | Windows-та жол тым ұзын | Жобаны `C:\dev\helpdesk` сияқты қысқа жолға көшіріңіз |
| `running scripts is disabled on this system` | PowerShell скрипттерге тыйым салған | `Set-ExecutionPolicy -Scope CurrentUser RemoteSigned` |
| `'uvicorn' is not recognized` | Виртуалды орта белсендірілмеген | `.venv\Scripts\activate`, содан кейін қайталаңыз |
| `address already in use` / 8000 порты бос емес | Басқа сервер іске қосылған | Ескісін Ctrl+C-мен тоқтатыңыз немесе `uvicorn app.main:app --port 8001` |
| `git push` → `403 Permission denied to <басқа аккаунт>` | Компьютерде басқа GitHub аккаунты сақталған | `git remote set-url origin https://<сіздің-логин>@github.com/southkz0717-source/helpdesk.git`, содан кейін push — кіру терезесі ашылады |
| `git push origin main` → `push declined due to repository rule violations` | Бұтақты қорғау | Бұл қате емес — солай болуы керек. Өзгерісті жеке бұтақта жасап, PR ашыңыз |
| DORA скрипті `403 rate limit exceeded` | GitHub API-дың анонимді лимиті (сағатына 60 сұраныс) | Бір сағат күтіңіз немесе Actions → DORA dashboard → Run workflow |
| `docker: failed to connect to the docker API` | Docker Desktop іске қосылмаған | Docker Desktop-ты ашып, жасыл белгіні күтіңіз |
| Docker-де жаңартқаннан кейін өтінімдер жоғалды | Контейнер томсыз іске қосылған (#7 инцидент) | `docker compose up -d` немесе `-v helpdesk-data:/data` пайдаланыңыз |
